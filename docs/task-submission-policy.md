# 任务提交防滥用基础层

## 作用范围

本模块只约束“已完成图片上传并准备创建队列任务”的提交动作。它不限制图片上传请求速率，也不替代 Caddy/WAF 的 IP 限流、验证码或存储容量配额。development/test 专用的模拟任务创建接口不会主动执行限额检查；它创建的任务仍属于同一用户，因此会被后续上传提交的用户级数据库计数看到。production 不注册该开发接口。

## 两类用户级限制

API 在上传提交事务中先锁定所属 `users` 行，再读取 PostgreSQL 中的任务状态：

- `RE3D_USER_MAX_PENDING_JOBS`：当前用户所有非终态任务的数量上限；
- `RE3D_USER_MAX_SUBMISSIONS_PER_24H`：当前用户滚动 24 小时内创建任务的数量上限，已成功、失败或取消的任务仍计入该窗口。

锁、限额判断、任务插入、上传状态更新和成功审计位于同一个事务。相同用户的并发提交因此会串行判定；第一个事务提交后，第二个事务才能继续并看到新任务。不同用户不共享这把行锁。重复提交同一个已经提交的上传仍按原任务幂等返回，不创建新任务，也不重复计数。

开发默认值为：

```dotenv
RE3D_USER_MAX_PENDING_JOBS=3
RE3D_USER_MAX_SUBMISSIONS_PER_24H=20
```

这些值不是生产产品策略。production 启动和就绪检查要求显式配置整数；`.env.production.example` 故意使用占位值，运维人员必须结合 GPU 吞吐、平均任务耗时和磁盘容量作出选择。

## API 拒绝合同

超限提交返回 HTTP 429，正文 `detail` 保持为前端可显示的字符串，并通过 `X-Re3D-Error-Code` 给出稳定机器码：

| 场景 | 错误码 | `Retry-After` |
|---|---|---|
| 非终态任务达到上限 | `PENDING_JOB_LIMIT_REACHED` | 不返回；等待已有任务终止 |
| 滚动 24 小时达到上限 | `SUBMISSION_WINDOW_LIMIT_REACHED` | 返回最早一条窗口内任务退出窗口前的秒数 |

限额拒绝发生在 manifest/request 写入之前，上传会话保持 `uploading`，用户可以在条件满足后重试。

## 审计边界

迁移 `0009_task_submission_policy` 新增 `task_action_events`。当前记录两类成功状态变更：

- `job_submitted`：队列任务与上传提交原子创建；
- `cancel_requested`：排队任务被直接取消，或运行任务首次写入取消信号。

审计包含用户、任务 UUID、执行模式、稳定原因码和数据库时间，不记录图片、文件路径、令牌、IP 或 User-Agent。重复取消和已终态任务取消不会写入重复事件。表暂不提供普通用户查询接口；管理员查询、事件保留期和清理命令仍需单独设计。

## PostgreSQL 验收

2026-09-30 使用无持久卷的一次性 PostgreSQL 18 完成以下验收：

- 两个线程对同一用户并发提交时，只允许一个任务进入队列；
- 稳定上传 API 在待处理任务达到上限时返回 429，且不插入任务、不改变上传状态；
- 取消任务后待处理名额释放，原上传可以重试提交；
- 重复提交已提交上传返回同一任务，不增加任务或审计记录；
- 两次任务终止后，第三次提交被滚动 24 小时限制拒绝，并返回 `Retry-After`；
- 两次成功创建与两次首次取消最终对应两条 `job_submitted` 和两条 `cancel_requested`；
- Alembic 从空库升级到 `0009`，再降级到 `0001` 并重新升级到 `0009` 通过。

验收脚本结束后自动删除容器和测试数据库，不连接或清理 `re3d_platform_dev`。
