# 单用户存储容量配额

## 1. 目标与边界

本模块限制一个账号能够持续占用的逻辑任务存储，避免多个上传会话或任务绕过单次 1 GiB 上传限制。它由 PostgreSQL 状态统一裁决，可供多个 API 进程共享；浏览器显示和预检只是交互提示，不能替代后端检查。

当前计费模型：

- 未提交上传：按尚未完成物理清理的 `job_uploads.total_bytes` 实际字节计费；
- 已提交任务：不再重复计算上传字节，改为按 `reconstruction_jobs.storage_reserved_bytes` 固定预留；
- 元数据、清单和小型报告不单独计费；
- 任务预留是容量控制估算，不是 Worker 文件系统硬上限。真实 Re3D 中间文件峰值仍需在目标 GPU 服务器用代表性数据测量并校准。

默认开发值为每用户 10 GiB、每任务预留 2 GiB。它们不代表生产推荐值。

## 2. 并发与生命周期

添加图片或提交任务时，事务先锁定上传记录，再锁定所属用户行。相同用户的并发请求因此在 PostgreSQL 中串行执行；后到的事务会看到先到事务已经提交的占用，不会同时越过配额。

提交时的投影占用为：

```text
当前用户占用 - 当前上传实际字节 + 每任务固定预留
```

只有投影值不超过用户总配额时，任务行、上传状态、请求清单和审计记录才在同一事务中完成。拒绝时上传保持 `uploading`，不会创建队列任务。

释放规则：

- 删除一张未提交图片后，其实际字节立即不再计费；
- 取消或过期上传只有在任务目录物理删除成功后才释放；删除失败会继续计费并由维护任务重试；
- 失败或取消任务只有在整个任务目录清理成功后才设置 `storage_released_at`；
- 成功任务必须完成 input、runtime、artifacts 三层清理后才释放预留；任一层失败时继续计费；
- 降低生产配额可能使已有用户暂时超额；此时读取仍可用，新增图片和任务提交被拒绝，直到清理释放占用。

`0014_user_storage_quota` 为任务增加预留字节和释放时间。历史已提交任务无法还原过去的中间文件峰值，因此迁移仅用对应上传的实际输入字节做保守的最小回填；迁移后新任务统一使用当前配置的固定预留。

## 3. 配置合同

```dotenv
RE3D_USER_STORAGE_QUOTA_BYTES=10737418240
RE3D_JOB_STORAGE_RESERVATION_BYTES=2147483648
```

生产环境必须显式提供两个整数。约束如下：

- 用户总配额必须为正数；
- 任务预留必须为正数且不得大于用户总配额；
- API 初始化和生产就绪检查要求任务预留至少为 1 GiB，并且不小于 `UPLOAD_MAX_TOTAL_BYTES`。

生产值应以代表性图片数量、分辨率、三分支运行时峰值、结果大小、并行任务上限和数据盘容量为依据。完成 Worker 空间实测前，不能把默认 2 GiB 当作可靠的最坏情况上限。

## 4. API 合同

`GET /api/v1/uploads/quota` 要求 Bearer access token，并返回：

- `quota_bytes`：账号总配额；
- `used_bytes`：上传实际字节与未释放任务预留之和；
- `remaining_bytes`：不小于零的剩余额度；
- `over_quota_bytes`：配置下调后可能产生的超额量；
- `upload_bytes`：未提交且未清理上传的实际占用；
- `reserved_job_bytes`：所有未释放任务预留之和；
- `job_reservation_bytes`：提交一个新任务需要的固定预留。

响应带 `Cache-Control: no-store`。添加图片或提交任务超过配额时返回 HTTP 507、`X-Re3D-Error-Code: USER_STORAGE_QUOTA_EXCEEDED` 和 `Cache-Control: no-store`。该响应不带 `Retry-After`；全局磁盘安全线仍使用独立错误码 `STORAGE_CAPACITY_FLOOR_REACHED` 和 300 秒重试提示。

## 5. 尚未覆盖

- Worker 运行中对目录实际字节数的硬限制或主动中止；
- 按用户或任务实时扫描文件系统并与数据库预留对账；
- 对象存储、分块上传、下载流量和并发配额；
- 管理员按用户调整配额的持久化覆盖值；当前是部署级统一配置；
- 目标服务器低磁盘告警和真实负载下的预留值校准。
